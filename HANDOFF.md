# CandyDownloader — handoff (Oct 2026)

Private Telegram bot that downloads video/audio/images from links (yt-dlp in-process, gallery-dl and aria2c as
subprocesses), branded per deployment (`OWNER_NAME`/`OWNER_EMOJI`). "Developer" = the person chatting; "owner" =
the bot's persona/admin. Python 3.12, python-telegram-bot 21.10, Docker Compose (bot + local Bot API server +
bgutil PO-token provider + optional warp proxy). The older architecture notes (rid as correlation key, local Bot API
volume, yt-dlp as a library so auto-update restarts the process) still hold.

## Run and test
- `docker compose up --build` after ANY code change (Dockerfile/requirements changes need it; so do code changes).
- Tests (383, offline): `cd bot && python -m unittest discover -s . -p "test_*.py" -t .` — stub packages for
  telegram / yt_dlp / httpx live in `bot/tests/stubs`; several tests drive real `ffmpeg`/`ffprobe`.
- Routine used for every change: write tests, then **mutation-check** (break the feature, confirm a test fails,
  restore). Always back files up to a stable dir and verify with `sha256sum -c` after restoring — a restore step that
  silently failed once left deliberate breakage in the tree.

## Conventions worth keeping
- Callback data `ns|action|...|<id>` (id last, < 64 bytes): `dl|sec`, `dl|sub`, `bt`, `hist`, `misc`, `s`, `nav`.
- `delivery_notes` (a list in the job's settings dict) = things to tell the person after delivery; `job_manager` sends them.
- Errors shown inside menus as a `⚠` line (a second `query.answer()` is ignored by Telegram).
- Anything user/site-controlled is HTML-escaped where it enters a template.
- Symbols, not emoji, for log/UI glyphs where possible (`ui/steplog.py` maps step text -> symbol: ✦ video, 𝄞 audio, ✄ clip ...).
- Callback namespace `tl|action|...|<rid>` = toolbox. Tool jobs are not logged to /history and have no link / send-as-file buttons (`quick_menu._markup` drops empty rows).
- Sections and subtitles are mutually exclusive (subtitles are for the whole video: wrong timing on a clip).
- ADHD Mode is unchanged: no menus, first link only, no picker.

## Decisions (developer's)
- No shared/global cookie. No inline mode. Subtitles: soft (embedded / .srt) AND burned-in. Burned-in re-encodes (x264 veryfast, audio copied), so it is capped by `BURN_MAX_SECONDS`; the image now has `fonts-noto-core` (Persian/Arabic, no CJK).
- The upload/share-link center is **not built here**: it lives in the developer's other project (candyflix, github.com/AmirHBuilds/candyflix); this bot will only be an **API client** (needs: endpoints, key header, upload method, limits, link shape).
- VPS blocking: developer will test provider/IP/WARP themselves; the bot already routes via WARP automatically when blocked.

- rev9 (2026-10-10): **Web app** (`bot/web/`, off unless `WEB_ENABLED=on`). Runs INSIDE the bot process (starlette + uvicorn in the same event loop), so it shares the one JobManager, queue, housekeeping and history with the bot. Web jobs use a virtual chat id (`utils/webchat.py`, far outside Telegram's range): `RoutingBot` swallows anything aimed at it, `JobManager._send_files` hands the files to `_adopt_for_web` (moved to `TMP_DIR/web/<rid>/`, downloaded in the browser, deleted after `WEB_FILE_TTL_MINUTES`), `finish_listeners` keep the outcome. Accounts (`web/accounts.py`): username + password (scrypt), sessions stored as hashes, 5 wrong passwords lock an account 15 min, a password change signs everyone out, the last active admin can't be removed/blocked. An account may be linked to a Telegram id and then IS that person (same settings, cookies, history as in the bot); an unlinked one gets internal id `-<account id>`. Security: HttpOnly + Secure + SameSite=Strict `__Host-` cookie, per-session CSRF header AND Origin check on every state change, login rate limits per address and per name (equal time for unknown users), strict CSP (no inline script/style; the page never uses innerHTML), nosniff, no-store on the API, files are served only by (job id, index) through the signed-in account, per-account active-job limit and disk allowance, `proxy` and `filename_template` are NOT editable from the web. Accounts are created: in the web (Admin tab, one-time password shown once, must be changed at first sign-in), in the bot by admins (`/webaccount add|reset|off|on|del|list`, private chat only, the message deletes itself), by anyone the bot lets in (`/weblogin`), or the first admin from `WEB_ADMIN_USER/PASSWORD`. Tests: 760 (163 new); two older test modules leaked fakes into others (`main.gate`, `ctl.time`) and were fixed.
- rev10 (2026-10-10): **Built-in download links** replace the external uploader (candyflix is gone; `web/uploader.py`, `web/secrets_store.py`, the `cryptography` dependency and `WEB_SECRET_KEY` were removed). `web/shares.py`: 🔗 Get a link COPIES the finished file to `data/shares/<token>/file` (so the link outlives the 2 h web download window and the bot's cache) and the web app serves it: `GET /s/<token>` is a small landing page (server-rendered, escaped, no script), `GET /s/<token>/<any name>` the file (attachment, Range supported; a request without Range or starting at byte 0 counts as a download, HEAD/resumes don't). Token = 256 random bits; unknown, malformed, expired and used-up links all give the same 404; public pages are rate-limited per address (240/min); `X-Robots-Tag: noindex`, no-store. Options per link: lasts 1 h–admin max (default 72 h, max 30 d), optional one-download-only. Admin > Download links: on/off, default/max hours, per-person allowance (default 2048 MB), list/delete everyone's links. Links belong to `user_id` (Telegram id, or `-account.id`), so a Telegram-linked web account and the bot show the same links; deleting a web-only account deletes its links; expired links and orphan folders are swept every 10 min. Web: Links tab (copy/delete) and a picker next to Download on finished files. Bot: 🔗 Get a link button (up to 5 files, link text escaped) and `/links` (list + 🗑 per link, owner-checked). Links need the web server on (`shares.available()` = `WEB_ENABLED` and not switched off) and `WEB_PUBLIC_URL` for the address put in the bot's messages (falls back to `http://localhost:<port>`). **Local debugging**: `docker compose -f docker-compose.yml -f docker-compose.local.yml up -d --build` (port 8080 on 127.0.0.1 only, insecure cookie, no proxy trust) or, with no Docker and no Telegram token, `cd bot && python web_dev.py` (data in `dev_data/`, prints the first admin password once). **VPS**: unchanged (`--profile web` with Caddy, `WEB_DOMAIN` + `WEB_PUBLIC_URL`).
- rev11 (2026-10-10): **Link restrictions.** Each link has `access`: 0 anyone with the link, 1 signed-in web accounts only, 2 only the maker (`shares.permits`), an optional **password** (scrypt, stored as `pw_hash`, never returned by any API; 4-100 chars), a download limit (1 = one-time) and a lifetime; the maker can tighten/extend later (`PATCH /api/shares/<id>`: access, max_downloads, hours, password, clear_password; owner-checked, never loosened below the admin minimum). Admin > Download links: default access and "never looser than" (`min_access`, e.g. force sign-in for every link). Refusals (wrong access/password) show a page that never names the file; they don't count as downloads; unlocking a password link sets a 1 h HttpOnly SameSite=Strict cookie `candy_dl` scoped to `/s/<token>` (server-side grant bound to the link id AND its current password hash, so changing the password ends every unlock); wrong passwords are throttled (5 per link+address per 15 min, 30 per link per hour). The password form posts to `/s/<token>/download` so the file name is not in the page before the unlock. Bot: the link message has buttons per file: `🔒 Sign-in only`, `1️⃣ Once`, `🗑` (`ua|<id>|login|once`, `ul|<id>`), and `/links` shows 🔒 👤 🔑 1️⃣ flags. Passwords are set in the web app only (not typed into a chat). Old databases get the two new columns on first use. Note: the session cookie is SameSite=Strict, so a signed-in person arriving from another app (Telegram) is not recognised on the first hit; the refusal page has an "I'm signed in - continue" button (a same-site click) that fixes it.

## Unverified in real use (check first after a rebuild)
1. `warp` container actually starts on the developer's setup (`docker compose logs warp`); the bot works direct if not.
2. ffmpeg `-progress` via yt-dlp's `external_downloader_args["ffmpeg_i"]` (clip progress bar). If not honoured the bar falls back to elapsed time and logs "No ffmpeg progress data".
3. Menu size vs real size mismatch (one report: 2.2 GB shown, ~750 MB fetched). Logs now print `Size estimate (best): ...` and `Size check: formats ..., announced ..., actually fetched ...` — compare them.
4. Opus "Conversion failed": cause unknown; the log now carries ffmpeg's real complaint, and the bot falls back (no cover art, then MP3).
5. Instagram: previews usually fail without cookies, which drops to the plain menu (no sizes/sections).
6. Telegram's built-in player probably doesn't show embedded subtitle tracks (the .srt option exists for that).
7. rev1: gallery-dl through `socks5h://warp:1080` (needs the rebuild for PySocks); Instagram/X blocks being recognised by the 403/429 wording; ADHD Mode on an X *image* post now shows one failed yt-dlp step before gallery-dl succeeds.
8. Many-file sends may hit Telegram flood limits (batches are capped at 50).
